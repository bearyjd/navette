# M2 Encoder Bridge + Viewer — Gate Report

Status: **CONDITIONAL PASS** — the pipeline is stable and leak-free, but
the milestone's headline symptom still reproduces end to end. See Decision.
Date: 2026-08-29
Host: Fedora Linux 43, kernel 6.19.11, KDE Plasma/Wayland

## Decision

**Conditional pass.** Everything M2 set out to build works and holds up: a
30-minute run with 22 encoder reconfigurations produced zero errors, zero
reconnects, zero dropped input and no leak in any component this milestone
owns. The client-side input path, which was responsible for the original
symptom, is now clean under measurement.

**But the symptom itself is not gone.** Typing during a resize still produces
repeated characters, reproducibly, at roughly one burst in six. The cause is
no longer where it was: it is now on the *server* side, and it is the same
shape as the client-side defect this milestone already fixed. Details under
"The remaining defect".

M2's plumbing is done. M2's user-visible goal is not, and the gate should not
be recorded as an unqualified pass while a user typing during a resize still
sees doubled characters.

## Why this report re-measures rather than cites

An earlier endurance run and tailnet measurement exist, dated 2026-08-26 and
recorded in `docs/HANDOFF.md`. They are **not** the evidence for this gate.

Four pull requests landed after them, and each changed something the gate is
supposed to be measuring:

| PR | change |
|---|---|
| #7 | the input path: pointer rescaling, key-edge handling, bridge dedup, and a minifb fork |
| #8 | decoding no longer blocks the runtime's I/O+time driver |
| #9 | minifb moved from our fork to upstream, two commits past ours |
| #10 | decoding moved onto a dedicated thread |

Citing a 2026-08-26 endurance run as evidence for this build would be citing a
different program. The endurance gate is therefore re-run against `52eea9d`.

The LAN/tailnet figures are a separate case and are carried forward with their
original date attached — see that section for exactly what is and is not still
believable about them.

## End-to-end keyboard verification

The oldest open item in the project was that no key-edge result had ever been
observed above the minifb layer. That is now closed, by typing into the viewer
and comparing against what the guest's stdin actually received, across the
whole path: injector -> nested compositor -> minifb -> navette-viewer ->
media socket -> navetted -> bridge -> wprsd -> guest.

| phase | injected | received |
|---|---|---|
| at rest | `quick` | `quick` — exact |
| rollover (each key released only after the next is down) | `brown` | `brown` — exact |
| during a live resize | `fox` x6 | 5 exact, **1 corrupted** |

## The remaining defect

The corrupted burst was `foxxxxxxx...` — roughly 95 repeats of the final
character. It reproduces across runs at about one burst in six.

It is **not** minifb, and **not** the client. Instrumenting the minifb
boundary showed six clean press/release pairs for that key, one per burst,
every press matched — the upstream two-phase fix is working. The viewer's own
path was clean in the same run: max poll cycle **7 ms**, zero dropped inputs,
zero retried releases, zero bridge-side releases for untracked keycodes, no
panic.

The repeat is also *bounded*, which is the diagnostic clue. `wprsd` advertises
`repeat_delay=200 repeat_rate=200` to the guest, so a guest repeats a held key
itself until the release arrives. A lost release repeats forever; a delayed
one repeats and then stops. This stops. So the release was **late, not lost**
— by roughly half a second.

That points at `run_bridge` in `crates/navetted/src/bridge.rs`, which handles
`MediaCommand::Input`, the debounced resize, `force_keyframe_on_all_streams`
and the scene events that composite and encode frames — all on one loop. A
resize restarts the encoder on that loop, and input queued behind it waits.

This is the same defect as the one fixed on the client in PRs #8 and #10:
delivery of input serialised behind expensive work on a shared loop. The fix
is likely the same shape too — get the encode off the path that also delivers
input.

## LAN/tailnet measurement

**Carried forward from 2026-08-26; not re-measured for this gate.**

A genuine second host (a DigitalOcean droplet in NYC3, reached over Tailscale
and forwarded to the media WebSocket through an SSH reverse tunnel) connected
to a live session. Baseline `ping` over the tailnet averaged 24 ms across 20
samples (min 12 ms, max 113 ms, mdev 22 ms) — real WireGuard-tunnelled
latency, not loopback.

Round trip from sending a `viewport_resize` to receiving the resulting
`stream_config` measured **768–832 ms, mean ~796 ms** across 7 clean samples.

What that number meant then, and still means: it is dominated by
application-side cost, not network transit. The 24 ms of network RTT is a
small fraction; the rest is the bridge's deliberate 100 ms resize debounce
plus the guest's own relayout and repaint. The practical implication for a
phone client is unchanged — a resize will not feel instant, and a drag-resize
UI wants a transitional treatment rather than assuming millisecond response.

**What is no longer safe to conclude from it.** The measurement used Firefox
as the guest and predates PRs #8 and #10, which removed a ~600 ms stall from
the same path. The *network* baseline (24 ms) is still valid, since nothing
in those PRs touches transport. The *end-to-end resize figure* should be
treated as an upper bound from an older build rather than a current
measurement, and re-taken against a second host before it is quoted as
current.

## Limitations, stated plainly

1. **No human has typed into a real navette window since the key fixes
   landed.** All key-edge evidence is from the minifb layer or a scripted
   harness. This is the oldest open item in the project and remains open.
2. **Input delivery latency is bounded by the decode queue.** Once
   `PACKET_QUEUE_CAPACITY` or its byte budget is exhausted, the connection
   task parks handing over a packet and stops draining input — the same stall
   PR #10 removed, deferred rather than eliminated. Closing it means the
   router owning its own task and the socket read never waiting on it.
3. **Five accepted-but-unfixed review findings** are recorded in
   `docs/HANDOFF.md` with concrete failure scenarios. None blocking; all real.
4. **XWayland does not start in this environment.** Pre-existing, unrelated to
   M2, and harmless for native-Wayland guests — but it would block anything
   needing X11 compatibility, and a stale `wprsd` holding a display makes it
   fail loudly rather than quietly.
5. **The measurement harness needs a guest that repaints continuously.**
   Firefox throttles paint when idle, which starves the decoder of access
   units so it never primes and the viewer never opens a window. That failure
   looks like a product bug and is not one; it cost two sessions before being
   identified.
